## ❌ OUT OF SCOPE for v2.2 (Deferred to v2.3+)

### Pause/Resume (→ v2.3)
```
❌ SessionStatus.PAUSED
❌ PausableExecutor interface
❌ Pause/Resume implementation
❌ State persistence during pause
```

**Rationale**: Complex feature requiring careful design. Better to release stable v2.2 first, then add pause/resume in v2.3 with real user feedback.

### Prometheus Metrics Exporter (→ v2.3)
```
❌ PrometheusExporter
❌ Metrics HTTP endpoint (/metrics)
❌ Prometheus text format
❌ Grafana dashboard templates
```

**Rationale**: Metrics collection will be in v2.2, but Prometheus export can be added later without breaking changes.

### Extended Event System (→ v2.3)
```
❌ SessionEvent hierarchy
❌ EventPublisher facade
❌ Custom event handlers
```

**Rationale**: Existing EventBus is sufficient for v2.2. Extended event system can be added incrementally.

### SDK Facade (→ v2.3-2.4)
```
❌ webharvest-sdk module
❌ WebHarvestSDK facade
❌ Fluent builder APIs
❌ SessionHandle abstraction
```

**Rationale**: Let v2.2 stabilize first. SDK can be built on top of stable v2.2 APIs.

### Parallel Execute Plugin (→ v2.4)
```
❌ ParallelExecutePlugin (@CorePlugin)
❌ Intra-session parallelism (fork-join)
❌ Task isolation within session
```

**Rationale**: Variant 2 from architecture. Complex plugin best developed after v2.2 is production-proven.

### Quota Enforcement (→ v2.3)
```
❌ QuotaPolicy (limits and thresholds)
❌ QuotaService (enforcement)
❌ QuotaExceededException
❌ Rate limiting
```

**Rationale**: Token tracking in v2.2 enables quota enforcement in v2.3.

## 📝 Notes

### Why Not Pause/Resume in v2.2?
Pause/Resume is complex because it requires:
1. Coordinated thread pausing at safe points
2. State preservation during pause
3. Resource cleanup/resume logic
4. Testing with real long-running scrapes

Better to:
1. Release v2.2 with solid session foundation
2. Get production feedback
3. Design pause/resume based on real usage patterns
4. Release in v2.3 when confident

### Why Basic Token Tracking?
v2.2 tracks token usage but doesn't enforce quotas. This allows:
1. Collecting real usage data in production
2. Understanding typical usage patterns
3. Designing appropriate quota policies for v2.3
4. Avoiding premature optimization

### Why No SDK Yet?
SDK facade is a contract with external developers. Better to:
1. Stabilize core APIs in v2.2
2. See how users actually use the APIs
3. Design SDK based on actual usage patterns
4. Release stable SDK in v2.3 with lessons learned
